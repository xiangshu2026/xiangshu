# 象数工坊 · 中国传统历法算法与规则推演引擎

纯前端、**完全离线**的传统历法推算工具。双击即用，不联网、不上传任何数据、不装依赖。

**技术内核**：干支推算 · 节气定位 · 真太阳时校正 · 藏干加权 · 地支关系矩阵（冲/合/刑/害/破/伏吟/成局）· 基于传统文献的规则计分体系。

七个模块：四柱历法 · 卦象推演 · 六爻纳甲 · 小六壬 · 时辰规则引擎 · 合盘计算 · 口径说明。

> ⚠️ **定位说明**：本项目是历法算法与规则推演的技术实现，用于传统文化研究与算法实践，不提供任何形式的预测服务或命运判断。所有输出为规则计算结果，仅供技术研究与个人参考。

> **不懂技术、只想直接用？** 看 [怎么用-新手说明.md](怎么用-新手说明.md)——下载一个文件双击就能用，不用安装任何东西。
>
> 各模块的完整功能说明、输入边界、算法口径见 [docs/功能详解.md](docs/功能详解.md)。

## 二、架构：为什么能在 Node 里跑测试

每个模块都是 UMD 包装，**浏览器和 Node 共用同一份代码**——这是 424 项测试能在命令行跑起来的前提：

```javascript
(function (root, factory) {
  if (typeof module === 'object' && module.exports) {
    module.exports = factory(require('./xs-data.js'), ...);   // Node
  } else {
    root.XS = root.XS || {};
    root.XS.Gacha = factory(root.XS.Data, ...);               // 浏览器
  }
})(typeof globalThis !== 'undefined' ? globalThis : this, function (D, BZ, Lib, Games, DL) {
  'use strict';
  // ...
});
```

分层：

```
index.html（DOM 骨架）
    ↓
app.js（渲染 + 事件 + localStorage）
    ↓
xs-bazi / xs-meihua / xs-liuyao / xs-xiaoliuren   ← 排盘层
xs-daily（日档唯一来源）/ xs-gacha（时辰层）      ← 评分层
xs-match / xs-avoid / xs-interp                   ← 解读层
    ↓
xs-data（基础表）/ lunar.js（历法底座）
```

## 三、这个项目最核心的东西：六层审计模型

做这个项目最大的收获不是代码，是一套**发现问题的方法**。它分了六层，而且**每一层都以为到底了，结果还有下一层**：

| 层 | 查什么 | 什么时候才想到查 |
|---|---|---|
| ① 实现是否正确 | 代码有没有写错 | 第一轮就在查 |
| ② 实现是否忠于规则 | 代码有没有按规则执行 | 第 25 轮都在查 |
| ③ **规则本身是否成立** | 规则有依据吗 | **第 28 轮才开始查** |
| ④ **规则之间的相对权重是否有依据** | 为什么冲是 6 不是 3？ | **第 32 轮才被指出** |
| ⑤ 子维度是否扫全 | 层内部还有没扫到的维度 | 第 20 轮 |
| ⑥ 代码路径是否分裂 | 同类项走了不同函数 | 第 22 轮 |

### 七类错误的完整账

33 轮对抗里，写引擎的一方输了 20 条。错误分类：

| 类型 | 次数 | 例子 |
|---|---|---|
| 漏项（维度没写全） | 4 | 漏合月支 / 漏刑害破 / 漏藏干 / 漏贵人宫位 |
| 方向反了（符号错） | 3 | 伏吟加分 / 合不算五行 / 冲按五行翻转 |
| 重复计分（违反自己立的规矩） | 4 | 三支成局却拆成两个半合 / 合与破双计 / 藏干与合化双计 / 冲贵人与冲年支双扣 |
| 双标（同一原则两处不一） | 2 | 冲用宫位合用五行 / 合贵人有加分冲贵人没有 |
| 层未扫 | 2 | 日层完全没扫 / 时辰层第五子维度没扫 |
| 路径分裂 | 2 | 合类两套系数 / 又写一遍公式 |
| 规则无依据 | 1 | 成局系数硬编码日支 1.0 |

**四类里三类都是「写过正确原则，但在别处没照做」。**

### 三条去重铁律

| 铁律 | 内容 |
|---|---|
| **A** | 同一对地支的多个关系 → **取烈度最高一条**（如丑未既冲又刑，只记冲） |
| **B** | 同一事实的多种说法 → **只计一次**（时支与年支同字且为贵人宫时，只计一次） |
| **C** | 关系成立本身**不计分**（合贵人 +3 后不再加「有合」分） |

### 最该记住的一句话

> **「知道规律」不等于「执行规律」。**

第 29 轮总结出「我修的是这一处的合，不是合这个类」，**第 30 轮立刻又犯了同类遗漏**。

所以真正的改进不能是「再承诺一次收齐」——

1. **在数据结构上让同类项聚在一起**（`REL_LEV` 里 he / banhe / gonghe / chengju 相邻 + 注释「这四个必须同规则」）
2. **加守卫测试**

**靠承诺没用，靠结构有用。**

## 四、工程实现：入口收敛

评分逻辑最初是「加法式」——每加一个维度就写一个 if 分支，还要记得乘系数、定符号、写注释（四件事）。错误率随维度数线性增长。

后来改成「收敛式」：**所有计分必须经过 `addRel()`**。

```
加法式：写 if 分支 → 记得乘系数 → 记得定符号 → 记得写注释    （四件事，会漏）
收敛式：只加参数                                              （一次机会）
```

而且「收敛」本身也分两层：

| 层次 | 做法 | 缺陷 |
|---|---|---|
| 函数收敛 | 抽出统一公式 `juScore()` | 仍要靠清单去改所有调用点，会漏 |
| **入口收敛** | 所有计分必须经过 `addRel()` | **不存在「忘了改」** |

验证方式也随之改变：不用列清单，直接 `grep 'hs +='` 看它出现在哪——只在 `addRel` 里就对了。**把人工检查法固化成测试**（10 处断言直接读 `xs-gacha.js` 源码，检查「不存在第二份公式」这类结构性质）。

> **可推广的原则：不要靠「记得调用」，要靠「绕不过去」。**

## 五、数值来源声明（重要）

> 本引擎的「关系烈度表」（冲 6 / 刑 3 / 害 2 / 破 1 / 合 2 / 伏吟 1.5 / 成局 4）与「宫位系数表」（日 1.0 / 月 0.6 / 时 0.5 / 年 0.4）：
> - **次序**（冲 > 成局 > 刑 > 合/半合/害 > 伏吟 > 破；日 > 月 > 时 > 年）**有传统依据**；
> - **具体比值是估定的，非古籍原文**；
> - 因此**绝对分数只有相对意义**（用于排序），不应被当作「准确值」；
> - **有定性依据的结论（酉时吉、卯时凶）比分数更可靠**。

## 八、开发方式说明（诚实标注）

这个项目的代码由 AI 辅助生成，**但架构决策、错误发现、规则取舍、验收标准由人主导**。具体地说：

- **AI 完成**：代码编写、测试脚本、文档整理
- **人完成**：设计「双 AI 对抗评审」机制、判断哪条质疑成立、决定口径调整（如「平档太多要收窄」）、定验收标准（不通过就不算完）

33 轮对抗里，另一个 AI 会话赢 20 条、写引擎的 AI 赢 3 条——**那些错误是被对抗逼出来的，不是自己发现的**。这个流程本身就是本项目最重要的产出之一。
